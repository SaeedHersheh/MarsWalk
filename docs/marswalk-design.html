Marswalk: system design and product requirements

Marswalk plans safe walking routes for astronauts on Mars, using real NASA terrain data, and models the radio and positioning link through relay orbiters. This page explains how the parts fit together, then states what the product must do.

1 System architecture

Three browser pages talk to one Python server. The server reads terrain from files on disk, relay-orbiter pass times from Postgres, and calls JPL Horizons for live geometry. Solid arrows are request and response; dashed arrows are data prepared ahead of time.

Solid blue-grey: request and response at runtime. Dashed grey: prepared ahead of time. Amber: external services.

What each part is responsible for

Planner (browser)

Shows the map and 3D scene, lets the user place waypoints, calls the route API, draws the route, slope profile, relay-contact timeline and the radio panel. It holds the simulation clock and plays the walk back.

Planning engine (server)

Turns the terrain grid into a cost surface, finds the route, then scores it: distance, time, slope mix, radiation dose, relay contact minutes. Safest, Balanced and Fastest are three weightings of the same search.

Comms router (server)

Holds messages in a queue, works out how long each one takes to cross the Earth–Mars gap, and releases Earth-bound or Pod-bound messages only when a relay orbiter is overhead.

Storage and pipelines

Heavy data is built once per site and read from disk. Pass times live in Postgres, with a JSON cache so the app still works when the database sleeps.

2 Data flows

Planning a walk

  1. Choose a site. The globe page opens the planner with ?site=<id>. A new site triggers POST /api/sites and the build pipeline.
  2. Load terrain. The client fetches the site metadata, base image tiles and the slope and heat layers from the server.
  3. Place waypoints. Habitat plus up to several stops. The client sends them with the policy (Safest, Balanced or Fastest) to the route endpoint.
  4. Search. The server prices each cell by slope tier. If no route exists under the maximum slope it relaxes the limit in steps (+4°, +8°) and says so in the warnings.
  5. Score. Distance, walking time, slope mix, radiation, and relay contact windows from the stored passes.
  6. Review. The client draws the route coloured by slope, the verdict, the profile and the timeline. The user can slide the departure time or jump to the best window.

Keeping pass data fresh

The pass fetcher asks Horizons for each orbiter's position over the next hours, computes elevation above the site's horizon, and writes pass start, end and peak elevation to Postgres. The server reads those rows; if the connection fails it reads data/passes_cache.json. Western longitudes must be sent to Horizons as negative east longitude in the 0–360 form.

3 Radio relay: how a message crosses Mars and Earth

The link is simulated, not real hardware. It uses real geometry: light time from Horizons (11.1 minutes one way when we tested) and real pass windows. The speed controls (×30, ×120, ×600) compress waiting time so a demo is watchable.

  1. Record. The astronaut holds push-to-talk. The browser records audio with MediaRecorder (microphone needs https or localhost) and posts it as base64 to /api/comms/send with the destination, Earth or Pod.
  2. Wait for a satellite. The message is accepted but sits in the queue until a relay orbiter is above the horizon. The panel says when the next pass starts.
  3. Uplink. During a pass the message goes up to the orbiter. For Earth, the server computes delay as light_min × 60 ÷ speed + 1.5 s.
  4. Delivery. When the delay has elapsed the receiving page polls /api/comms/inbox and fetches the audio from /api/comms/audio/<id>. Mission control plays it.
  5. Reply path. Earth to astronaut messages wait at the orbiter until the next pass, then /api/comms/deliver/<id> releases them to the planner.

Practice mode pretends a satellite is overhead so the flow can be tested when no real pass is near. /api/comms/config sets the speed and /api/comms/clear empties the queue.

5 Product requirements document

Problem

A person walking on Mars cannot call for help in real time. Messages to Earth take 4 to 24 minutes one way. Navigation has no GPS. Radiation, steep slopes and heat all add risk, and the shortest path is often the most dangerous one. Planners need to see, before leaving the habitat, which route is safest and when a relay satellite can carry their voice.

Product

Marswalk is a web app that plans an extravehicular walk anywhere on Mars from real NASA terrain data, picks routes that prefer flat ground and low exposure, shows when relay orbiters are overhead, and simulates voice messages crossing the relay with the true Earth light delay.

Users

EVA planner

Draws a route, compares Safest, Balanced and Fastest, and decides departure time.

Astronaut (on phone)

Sees the route and the next satellite pass on a small screen and sends push-to-talk messages.

Mission control

Receives astronaut audio after the light delay and sends replies that wait for a pass.

Judges and students

Open the planner, press play, and understand in one minute why the route avoids the steep ground.

Goals

  • Produce a route that avoids steep ground first and relaxes the limit only when no other route exists, and say when it did.
  • Show radiation, time, slope mix and relay contact for every route in one summary.
  • Work at any chosen location on Mars, not only Jezero.
  • Make the relay-delay idea tangible with audio and a speed control.
  • Be readable on a phone and on a projector.

Non-goals

  • Not flight software. It is a planning and education prototype.
  • No real radio hardware, no real orbiter command link.
  • No multi-user accounts or authentication in this version.
  • No dust storms, thermal suit limits or consumables model.

  1. Prototype (done). Jezero planner, routing, radiation, relay timeline.
  2. Anywhere on Mars (done). Globe, site builder, MOLA global elevation.
  3. Relay radio and redesign (done). Voice delay, mission control, NASA-style interface, realistic 3D.
  4. Demo hardening (next). Public link, route sharing, positioning accuracy view, tests.

Open questions

  • Where will the public demo run: a tunnel from the team laptop, or a small cloud VM?
  • The position fix ignores terrain blocking the orbiter in manual mode and assumes height is known from the terrain map. Is that acceptable for the demo?
  • Does the team want NASA's own 3D models in place of the procedural ones? That needs a download approval.
